Embr Charts 8.3/main: architecture, ApexCharts coverage, and extension map

Developer-focused research for the Ignition 8.3 chart module: the actual three component surfaces, exact schema and palette coverage, the official ApexCharts comparison, and the files required to add a new chart.

Date2026-09-24
Branchorigin/8.3/main
Module@embr-modules/charts 6.0.4
Runtimeapexcharts 3.54.1

Executive answer

  • 8.3/main still exposes three Perspective components: modern ApexCharts, Chart.js, and Kyvis-Labs-compatible ApexCharts Legacy.
  • The chart implementation is unchanged from 8.1/main. The branch changes Ignition packaging and compatibility metadata, not modern Apex schemas, recipes, renderers, thumbnails, or Chart.js plugin registration.
  • Modern Apex advertises 16 distinct chart types in its schema and registers 19 non-base palette recipes. The runtime forwards the configured type to the pinned ApexCharts library rather than enforcing an Embr allowlist.
  • Range Bar is schema-capable but palette-hidden: timeline.props.json and its thumbnail exist, but no Timeline PaletteEntry is registered.
  • Pie is mislabeled: the visible pie recipe starts with type: "donut". There is no distinct modern Pie or Donut palette pair.
  • For a standard new Apex type, touch the schema, variant JSON, thumbnail, and ApexCharts.kt. Upgrade the Apex dependency first if the installed ApexCharts version cannot execute the requested type.

1. Codebase map

The module is a four-project Ignition package. Common owns the public descriptors, schemas, and palette resources; Gateway and Designer register those descriptors; Web packages the browser renderers.

Modern Apex path

  1. ApexCharts.kt declares ID embr.chart.apex-charts, category chart, and the shared browser resource.
  2. The inherited schema loader resolves /schemas/components/embr.chart.apex-charts/props.json.
  3. Each registered PaletteEntry loads the matching variant JSON and thumbnail using its variant ID.
  4. web/src/client.ts registers ApexChartsComponentMeta.
  5. The reducer reads type, options, series, events, redraw, and style.
  6. The React wrapper writes the top-level type into options.chart.type, creates new ApexCharts(...), and updates or recreates the instance.

2. Complete ApexCharts support matrix

The official chart-types page lists 26 user-facing rows. Column and Bar share chart.type: 'bar'; Mixed uses Line as its base type. The matrix keeps the catalog rows visible while separating schema, palette, and runtime boundaries.

https://apexcharts.com/docs/chart-types/ "ApexCharts supports 20+ chart types. Each is controlled by the chart.type option and has its own data format and configuration namespace under plotOptions." Official page: 18 axis rows + 8 non-axis rows = 26. After collapsing Bar/Column and Mixed/Line: 24 distinct runtime type values.

How to read the status

  • Schema: type appears in the modern chart_type suggestions. It is a string with suggestions, not a hard enum.
  • Palette: a Kotlin PaletteEntry is registered, with matching variant JSON and thumbnail.
  • Runtime: the renderer passes the value to ApexCharts. Source proves pass-through, not that every newer official type works with the pinned ApexCharts 3.54.1.

3. Chart.js and Legacy Apex coverage

Chart.js: embr.chart.chart-js

Schema suggestions: bar, boxplot, bubble, dendrogram, doughnut, euler, forceDirectedGraph, funnel, graph, line, matrix, pcp, pie, polarArea, radar, scatter, sankey, tree, treemap, venn, violin, and wordCloud.

Registered palette recipes: base, bar, bubble, boxplot, doughnut, line, pie, polararea, radar, and violin.

The global plugin registry is wider than the palette: it registers boxplot/violin, graph/tree, matrix, PCP, Sankey, treemap, funnel, Venn/Euler, word cloud, zoom, annotation, data labels, drag data, hierarchical scale, stacked100, and other plugins. The target tree has no matching variant schema/thumbnail for many of those runtime types.

Legacy Apex: kyvislabs.display.apexchart

Schema enum: line, area, bar, radar, histogram, pie, donut, radialBar, scatter, bubble, heatmap, candlestick, polarArea, rangeBar, treemap, rangeArea, and boxPlot.

Palette recipes: base, line, pie, radar, and timeseries. The component has 19 declared events, a separate browser class renderer, and a specialized gateway delegate. It is not the modern component contract.

5. How to add chart support

Q: What files do I touch to add Waterfall, Gauge, Violin, or another standard Apex type?

  1. Verify the installed library. modules/charts/web/package.json pins apexcharts 3.54.1. Upgrade the dependency and feature imports first if the requested type is newer than that runtime.
  2. Update the schema. Add the exact library spelling to common/src/main/resources/schemas/components/embr.chart.apex-charts/props.json under chart_type. Add type-specific data/plot options if the existing schema does not represent the series shape.
  3. Add a complete recipe. Create .../embr.chart.apex-charts/variants/<id>.props.json with type, valid series, options, and optional style/redraw.
  4. Add the thumbnail. Create .../designer/src/main/resources/images/components/embr.chart.apex-charts/thumbnails/<id>.png.
  5. Register the palette. Add a PaletteEntry in ApexCharts.kt and call .addPaletteEntry(...) in the descriptor.
  6. Do not add a renderer branch by default. The modern wrapper already forwards the type and recreates the chart when it changes.
  7. Smoke the real component. Test the drop-in recipe, type transition, series update, options update, lifecycle events, and any exposed proxy method.
  8. Document the release. Update modules/charts/CHANGELOG.md and document the compatibility boundary if a dependency upgrade was required.
FIX: Do not advertise a new runtime type until the pinned ApexCharts dependency and its required feature module can execute it.

Q: What is the minimum change set for a type already supported by the installed library?

  • common/src/main/resources/schemas/components/embr.chart.apex-charts/props.json
  • common/src/main/resources/schemas/components/embr.chart.apex-charts/variants/<id>.props.json
  • designer/src/main/resources/images/components/embr.chart.apex-charts/thumbnails/<id>.png
  • common/src/main/kotlin/com/mussonindustrial/ignition/embr/charts/component/chart/ApexCharts.kt
  • modules/charts/CHANGELOG.md

No new Gateway or Designer context is needed for a standard modern Apex type. Both contexts already register the existing descriptor.

Q: When do I touch TypeScript?

  • New root props/reducer shape: ApexChartsComponent.tsx plus schema.
  • Custom series normalization or compatibility: react/ApexCharts.tsx.
  • New Perspective events: schema definitions plus client event wiring.
  • New script methods: the client delegate and possibly a custom Gateway delegate.

Q: How do I add a Chart.js type?

  1. Add the package to web/package.json and the lockfile.
  2. Import/register its controller, element, scale, or plugin in web/src/components/chartjs/plugins/index.ts.
  3. Add the type and plugin-specific data/options shape to embr.chart.chart-js/props.json.
  4. Add variant JSON, thumbnail, PaletteEntry, and descriptor registration in ChartJs.kt.
  5. Exercise a valid plugin-specific dataset in a real client session.

Q: When is a new component ID required?

Only for a genuinely new Perspective component. Then add the JVM descriptor, matching schema, browser renderer/meta, barrel exports, client.ts registration, both Gateway/Designer context lists, assets, dependencies, and any needed delegate.

Q: How should I test a new chart?

The target branch has no chart test/spec files and permits an empty test set. Use a real Perspective Designer/Gateway session for initial proof. Add a permanent test when behavior changes, covering schema parsing, type pass-through, rendering, update, type change, and any special event/proxy behavior. A registration-only test is insufficient.

6. Developer Q&A quick reference

Where is the public contract?

common/src/main/resources/schemas/components/<component-id>/props.json. The descriptor ID selects the resource path.

Where is the visible palette?

common/.../component/chart/ApexCharts.kt. It is explicit Kotlin and is not generated from the variant directory.

Where does modern Apex render?

web/src/components/apexcharts/ApexChartsComponent.tsx and react/ApexCharts.tsx.

Does a new type need a new Gateway component?

No, if it uses the modern component. Gateway registration and the JavaScript proxy already exist.

Why is the type list not strict?

The schema defines suggestions on a string. The reducer reads a string and the renderer forwards it. The external library is the runtime boundary.

Should Legacy Apex change too?

Only for an explicit compatibility requirement. It has a different ID, schema, renderer, events, and delegate.
