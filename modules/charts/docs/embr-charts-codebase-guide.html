Embr Charts: architecture, ApexCharts coverage, and extension map

A repository-grounded guide to the Ignition chart module: what ships today, where each chart type is represented, and the smallest safe file set for adding another chart.

Date2026-09-24
Scopemodules/charts
MethodRepository read + official chart catalog
SourceApexCharts chart-types page

Executive answer

  • Embr Charts is a three-component Ignition module: modern ApexCharts, Chart.js, and Kyvis-Labs-compatible ApexCharts Legacy.
  • Modern ApexCharts is largely configuration-driven. The browser wrapper passes the configured type to the pinned ApexCharts library; it does not contain a chart-type switch.
  • The official page lists 26 chart rows / 24 distinct chart.type values. The modern Embr schema suggests 16 distinct values, and the Kotlin descriptor registers 18 non-base palette recipes.
  • Coverage is not identical across layers. A type can be in the schema, present as a palette recipe, or only pass through at runtime. The report marks each layer separately.
  • Two concrete drift points need attention: the pie recipe actually starts with type: "donut", and the timeline range-bar recipe exists but is not registered in the Kotlin palette.
  • For a standard new ApexCharts type, the normal change set is: schema suggestion/definitions, one variant JSON file, one thumbnail, and one PaletteEntry registration. A renderer change is normally unnecessary.

1. Codebase map

The module is assembled from four Gradle subprojects. The common project owns the public Perspective contract; gateway and designer projects register it at runtime; the web project renders the browser components.

Modern ApexCharts request path

  1. The descriptor ID is embr.chart.apex-charts.
  2. The descriptor calls the inherited schema loader, which resolves /schemas/components/embr.chart.apex-charts/props.json.
  3. The designer adds each Kotlin PaletteEntry; PaletteEntry resolves the matching variant JSON and thumbnail by the same variant ID.
  4. The browser bundle registers ApexChartsComponentMeta.
  5. The component reducer reads type, options, series, events, redraw, and style.
  6. The React wrapper merges the configured type into options.chart.type, creates new ApexCharts(container, config), and handles updates/redraws.

2. Complete ApexCharts support matrix

The official catalog currently lists 26 named chart rows. Column and Bar share chart.type: 'bar'; Mixed uses Line as its base type. The matrix keeps those distinctions visible instead of treating the list as 26 independent runtime strings.

https://apexcharts.com/docs/chart-types/ "ApexCharts supports 20+ chart types. Each is controlled by the chart.type option and has its own data format and configuration namespace under plotOptions." Official rows counted from the page: 18 axis rows + 8 non-axis rows = 26. Distinct chart.type values after collapsing Bar/Column and Mixed/Line: 24.

Coverage definitions

  • Schema: the type appears in embr.chart.apex-charts/props.json suggestions. The field is a string with suggestions, not a strict enum.
  • Palette: a Kotlin PaletteEntry is registered, with a matching variant JSON and thumbnail.
  • Runtime path: the modern renderer forwards the string to the external ApexCharts library. Repository source proves the pass-through; it does not independently prove that every external-library type renders in this pinned version.

Counted conclusions

16 / 24

Distinct official chart.type values are suggested by the modern schema.

The field is not an enum, so this is an editor/advertising contract, not runtime enforcement.

18 non-base

Modern Kotlin palette recipes are registered, including recipe-only IDs such as column, funnel, mixed, and slope.

timeline is a nineteenth non-base variant resource but is not registered.

16 direct

Official rows have a direct registered recipe, treating Column, Funnel, and Mixed as recipe realizations and excluding the Pie/Donut mismatch.

The exact mapping is intentionally conservative.

8 not surfaced

violin, raincloud, streamgraph, waterfall, dumbbell, gauge, and pyramid are absent from the modern schema suggestions; Funnel is recipe-only.

[INFERENCE] Runtime may accept some values through ApexCharts, but repository evidence does not prove it.

Important naming details

  • boxplot, polararea, radialbar, and rangearea are palette IDs; the payload type remains the ApexCharts spelling boxPlot, polarArea, radialBar, and rangeArea.
  • column and funnel use root type bar with orientation/plot options.
  • mixed uses root line and per-series types.
  • slope is an Embr recipe using line plus isSlopeChart: true; it is not one of the 26 official rows on the cited page.

3. Chart.js and Legacy Apex coverage

The module is not Apex-only. Chart.js has a wider third-party plugin surface, while Legacy Apex is a separate compatibility contract and should not be changed as a side effect of modern Apex work.

Chart.js component: embr.chart.chart-js

Schema-level type suggestions: bar, boxplot, bubble, dendrogram, doughnut, euler, forceDirectedGraph, funnel, graph, line, matrix, pcp, pie, polarArea, radar, scatter, sankey, tree, treemap, venn, violin, and wordCloud.

Registered default palette recipes: bar, bubble, boxplot, doughnut, line, pie, polararea, radar, and violin, plus base.

The web plugin registry also registers third-party controllers/elements for boxplot/violin, graph/tree variants, matrix, parallel coordinates, Sankey, treemap, funnel, Venn/Euler, word cloud, stacked 100, zoom, annotations, and other plugins. That means schema/runtime coverage is broader than the nine visible default recipes.

4. How to add chart support

Choose the narrowest path that matches the request. A new chart type in the existing ApexCharts component is not the same as a new Perspective component.

Q: I want to add a standard ApexCharts type such as Waterfall, Gauge, or Violin. What files do I touch?

  1. Confirm the pinned library. Check modules/charts/web/package.json and yarn.lock. The modern renderer uses the external apexcharts package; upgrade the dependency first if the pinned version does not support the requested type.
  2. Advertise the exact ApexCharts spelling. Add waterfall, gauge, or violin to modules/charts/common/src/main/resources/schemas/components/embr.chart.apex-charts/props.json under the chart_type suggestions. If per-series type values also need it, confirm the shared schema definition is intended for that field.
  3. Add a sample variant. Create .../embr.chart.apex-charts/variants/<variant-id>.props.json with the root type, representative series, and the type-specific options. Follow the shape of base.props.json.
  4. Add the thumbnail. Create .../designer/src/main/resources/images/components/embr.chart.apex-charts/thumbnails/<variant-id>.png. The filename must exactly match the variant ID.
  5. Register the palette entry. Add a PaletteEntry in ApexCharts.kt, then add .addPaletteEntry(VARIANT_...) to the descriptor.
  6. Normally do not change the renderer. ApexChartsComponent.tsx already forwards the type and react/ApexCharts.tsx already handles type changes by destroy/redraw.
  7. Add proof. Verify the drop-in component in Designer/runtime, then change its type and update series/options. Add a focused test if wrapper or lifecycle behavior changes.
  8. Update release documentation. Record the new palette/type in modules/charts/CHANGELOG.md; update the web changelog only when web behavior or dependencies change.
FIX: Keep the variant ID, JSON filename, thumbnail filename, and Kotlin registration in lockstep. A schema suggestion alone does not create a visible palette entry.

Q: What is the minimum file set for a type already supported by the external ApexCharts library?

  • modules/charts/common/src/main/resources/schemas/components/embr.chart.apex-charts/props.json
  • modules/charts/common/src/main/resources/schemas/components/embr.chart.apex-charts/variants/<id>.props.json
  • modules/charts/designer/src/main/resources/images/components/embr.chart.apex-charts/thumbnails/<id>.png
  • modules/charts/common/src/main/kotlin/com/mussonindustrial/ignition/embr/charts/component/chart/ApexCharts.kt
  • modules/charts/CHANGELOG.md for release notes

No new Gateway or Designer context is needed. Both contexts already register the ApexCharts component descriptor.

Q: When do I need to touch the TypeScript renderer?

Touch the renderer only when the new chart needs behavior beyond the existing ApexCharts contract:

  • new root props or a different reducer shape: ApexChartsComponent.tsx and props.json;
  • custom series preparation, compatibility normalization, or redraw semantics: react/ApexCharts.tsx;
  • new Perspective events: schema event definitions plus the component event wiring;
  • new client scripting methods: the client delegate and, if needed, a Gateway delegate.

Q: How do I add a new Chart.js type?

  1. Add the package to modules/charts/web/package.json and update the lockfile.
  2. Import and register its controller/element/plugin in modules/charts/web/src/components/chartjs/plugins/index.ts.
  3. Add the type to embr.chart.chart-js/props.json and add type-specific data/options definitions if the plugin shape is not covered.
  4. Add .../embr.chart.chart-js/variants/<id>.props.json and the matching thumbnail.
  5. Add the Kotlin PaletteEntry in ChartJs.kt.
  6. Exercise the real chart with a valid plugin-specific dataset; do not rely only on the schema passing.

Q: When is a new component ID required?

Create a new ID only for a genuinely different Perspective component, not for another ApexCharts type. The new component then needs all of the following:

  1. a JVM PerspectiveComponent descriptor;
  2. common/src/main/resources/schemas/components/<new-id>/props.json;
  3. a browser ComponentMeta and renderer;
  4. exports and ComponentRegistry.register(...) in the web entrypoint;
  5. Gateway and Designer context registration;
  6. icons, thumbnails, dependencies, and a lifecycle-specific delegate if required.

Q: How do I test a new chart?

The repository has no chart-specific test files under the Vite source globs, and the test config permits an empty test set. For a new chart, do not treat a passing typecheck as proof. At minimum:

  1. drop the variant into a Perspective Designer project;
  2. render its sample data in a real client session;
  3. change the configured type;
  4. change series and options while mounted;
  5. exercise any exposed lifecycle or scripting methods;
  6. check the console for ApexCharts errors and verify destroy/re-render behavior.

Add a permanent focused test when the implementation changes or the bug is reproducible. A test that only checks registration or file existence is insufficient.

5. Developer Q&A quick reference

Where is the public component contract?

common/src/main/resources/schemas/components/<component-id>/props.json. The descriptor ID selects the resource path.

Where is the visible palette list?

common/.../component/chart/ApexCharts.kt. It is explicit Kotlin, not generated from the variant directory.

Where does the chart render?

web/src/components/apexcharts/ApexChartsComponent.tsx and .../react/ApexCharts.tsx.

Does a new type need a new Gateway component?

No, if it uses the existing modern component. Gateway registration already exists; the external chart instance is already exposed through the modern JavaScript proxy.

Why is a type suggestion not a strict allowlist?

The modern schema defines a string with suggestions. The reducer reads a string and the renderer passes it through. External library behavior is the remaining boundary.

Should I update Legacy Apex too?

Only if compatibility is an explicit requirement. Its ID, schema, client implementation, events, and delegate are separate.

7. Verification boundary

This artifact is a repository investigation, not a runtime certification. The following were verified from source:

  • module subproject inclusion and packaging metadata;
  • component IDs, descriptor palette registrations, schema resources, and registration contexts;
  • the modern ApexCharts type pass-through and update/redraw lifecycle;
  • the complete local schema/palette lists and the cited ApexCharts official catalog;
  • the absence of matching chart test files under the configured web source globs.

Not verified here:

  • visual rendering of every chart in a running Ignition Gateway/Designer session;
  • external ApexCharts behavior for every official type at version 3.54.1;
  • actual client-side scripting/event behavior in a deployed module;
  • whether every listed Chart.js package is active; the source registration list is the stronger evidence for active controllers/plugins.

Method: read-only source inspection of modules/charts and directly related Perspective integration files, plus the ApexCharts official chart-types page. Evidence blocks quote repository text or source paths verbatim. Findings and machine-readable data are intentionally kept in one-to-one agreement.
